Integration brief

Verified payment reputation for AI agents

A seller's score only changes when the buyer's own wallet signs the update, so a seller cannot inflate its own record. This brief shows how an agent platform can check that record before it signs a payment.

Solana devnet. Independent project: not a product of any agent platform, and no partnership is implied. Last updated 5 November 2026.

What we are asking for
  1. An activation token, so we can deploy a read-only App to Aomi Build (aomi-build connect requires one).
  2. Whether App tools may make outbound HTTPS calls, and the tool timeout. Our reputation API can take up to about 50 seconds to answer when its free-tier host is asleep.
  3. Whether an App can read Solana devnet data.

The problem

An agent that pays another agent has no way to tell a seller with a real track record from one that paid itself. A high score built from a single wallet looks the same as one built from many independent buyers.

What a platform gets

Reputation lookup

Read-only. Score, tier, confidence and vetting checks for any seller. No signing, no wallet access.

Policy gate

A proceed or do_not_pay recommendation under a Standard or Strict policy, with plain-language reasons.

Buyer-signed record

After payment the buyer's wallet signs the reputation update, in the same transaction as the payment.

The two tools

ToolReturns
check_agent_reputation(seller, policy?)Score, tier, confidence, vetting checks, recommendation and block reasons.
list_top_agents(limit?)Sellers ranked by reputation, with tier and confidence.

Standard policy: reputation 80 or more, and buyer independence must not fail. Strict adds confidence of Medium or higher.

What exists today

  • Live demo of the full flow: routex402.xyz/demo.html. The lookup and policy use live data, the simulation step is mocked, and the final step is a real devnet payment to a demo seller.
  • Read-only Aomi App, written in Rust against aomi-sdk 7.0.0. It compiles and its unit tests pass. It is not deployed yet: github.com/msurfx/routex402-aomi-app.
  • On-chain proof. One settled demo payment, where payment, protocol fee and reputation update are a single transaction signed by the buyer: view on Solscan. Program: 6pp5jD...P62vjt.
  • Explorer with a vetting page per agent: routex402.xyz.

How it fits in an execution flow

  1. The agent states its intent to pay a seller.
  2. It calls check_agent_reputation.
  3. A policy decides whether to continue. In the demo, our own top-scoring agent is blocked: every one of its payments came from a single buyer.
  4. The platform simulates and the user approves, as it does today.
  5. The buyer signs the payment and the reputation update together.

Limits you should know about

  • Devnet only, with a small number of demo agents. Scores are evidence, not a guarantee.
  • For some agents the distinct buyer count was not recorded, so confidence shows Unknown.
  • The contract has not had an external audit. Mainnet is planned only after one.
  • The tool shapes are a proposal, not a published API.

What comes next

  • A versioned public API with server-side pagination.
  • An unsigned-transaction endpoint so a platform can build the payment itself.
  • Open seller registration.
  • Contract hardening and an external audit, then mainnet.
